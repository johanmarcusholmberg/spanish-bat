2. Session-card UI

Goal:
Make guided practice sessions feel like a native mobile learning flow.

The session experience should feel like:
One card. One task. One clear action.

Avoid:
- Dense pages
- Long forms
- Too many buttons
- Desktop-heavy layouts
- Analytics-style UI during practice

Recommended session-card structure:
- Progress indicator, for example “3 of 8”
- Activity label, for example “Echo”, “Build”, “Review”, “Listen”
- Main prompt/question
- Audio/play button where relevant
- One focused interaction
- Primary continue/check button
- Optional “I don’t know” or “Skip for now”
- Gentle feedback after answer
- Clear next step

Session cards should support:
- vocabulary recall
- Echo/listen-and-repeat
- sentence building
- grammar correction
- short reading/dialogue
- weak item review
- pronunciation/speaking steps

UX tone:
- Warm
- Encouraging
- Simple
- Not childish
- Not technical

Example copy:
- “Listen and echo this phrase”
- “Build the sentence”
- “Try saying it out loud”
- “Almost — let’s echo it once more”
- “Nice, this word is getting stronger”

Acceptance criteria:
- Guided sessions use a card-based layout suitable for mobile.
- Each step has one primary task.
- Touch targets are mobile-friendly.
- The same session logic can support different activity types.
- The UI reinforces “Echo the language.”

3. Resume session

Goal:
Users should be able to leave a session and return without losing progress.

Mobile users are often interrupted, so the app must save session state frequently.

Implementation requirements:
- Save current session id/type.
- Save current step index.
- Save completed answers.
- Save mistakes already recorded.
- Save weak items already updated.
- Save session start time and last updated time.
- Avoid duplicate progress if the session is resumed.
- Allow user to resume or start fresh.
- Show “Continue today’s practice” when a resumable session exists.

Persistence:
- Use the existing persistence layer if one exists.
- If not, add a clean abstraction that can later work with local storage on web and AsyncStorage/native storage on mobile.
- Do not hard-code browser-only APIs directly into session logic.
- Wrap storage access in a reusable service/hook.

Suggested abstractions:
- sessionStorageService
- useResumableSession()
- saveSessionProgress()
- loadActiveSession()
- clearCompletedSession()

Acceptance criteria:
- User can leave and resume a guided session.
- Resuming does not duplicate completion/progress.
- Today screen can show an active/resumable session.
- Storage logic is abstracted for future mobile compatibility.

4. Offline cache foundation

Goal:
Add a foundation for offline-friendly learning, especially for daily review and weak items.

Do not try to build a complete offline system if that is too large. Start with safe caching architecture.

Offline-friendly areas:
- Today’s planned session
- due review items
- weak words/phrases
- basic vocabulary metadata
- user’s current level
- last known progress summary
- fallback practice items

Implementation requirements:
- Add a cache abstraction that can work on web now and native mobile later.
- Avoid direct dependency on browser-only APIs inside learning logic.
- Cache enough data for a short review session.
- Add safe fallback behavior if online data is unavailable.
- Track whether cached data may be stale.
- Do not overwrite server/source-of-truth progress incorrectly when offline.

Suggested abstractions:
- learningCacheService
- getCachedTodaySession()
- cacheTodaySession()
- getCachedWeakItems()
- cacheWeakItems()
- getOfflineFallbackSession()

Acceptance criteria:
- There is a clear caching foundation for daily practice.
- The app can show useful learning content even if fresh data cannot be loaded.
- Cache logic is separated from UI.
- Future native storage support will be straightforward.

5. Microphone/audio permissions foundation

Goal:
Prepare Murcielingo for strong mobile Echo and pronunciation features.

Echo should become a first-class mobile feature:
Listen → Repeat → Compare → Try again → Use it

Implementation requirements:
- Add a microphone/audio capability abstraction.
- Do not assume browser APIs will work the same in native mobile.
- If full recording is not currently implemented, create a safe foundation with placeholders.
- Add permission-aware UI states:
  - microphone not requested
  - requesting permission
  - permission granted
  - permission denied
  - recording unavailable
- Add graceful fallback:
  - user can continue without recording
  - user can mark confidence manually
  - user can still listen and repeat

Suggested abstractions:
- audioPermissionService
- useMicrophonePermission()
- canRecordAudio()
- requestMicrophonePermission()
- startRecording()
- stopRecording()
- playbackRecording()

UI guidance:
- Keep permission request contextual.
- Do not ask for microphone permission on app launch.
- Ask only when the user enters a speaking/Echo step that needs recording.
- Explain why the permission is needed in plain language.

Example copy:
- “Murcielingo uses your microphone so you can echo phrases and hear your progress.”
- “You can still practice without recording.”
- “Try saying it out loud, then mark how it felt.”

Acceptance criteria:
- Speaking/Echo steps are permission-aware.
- App does not break if microphone access is denied.
- Audio/recording logic is abstracted for future native implementation.
- Echo can work with or without recording.
